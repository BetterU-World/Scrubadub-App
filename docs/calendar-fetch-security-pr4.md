# Calendar feed security (PR #4)

## Audit before implementation

Audited main 66bfdb5 (contains merged #270, #271 and #272; no deployment inference).
Owner entry called owner/session/company-scoped create/update mutations. They stored the URL verbatim without destination validation. The indexed property query required active same-company staff, but returned the entire record, including the bearer URL and persisted error. Owners saw the complete URL and editing prefilled it. No URL local-storage cache was found. Internal beginSyncAttempt genuinely needs the URL; the unused internal connection query does not. Replacement already increments feedRevision and fences pending/in-flight work; removal cancels pending work and deletes the connection, preserving historical reservations.

The Node action used global fetch with automatic redirects, a 30-second signal, and unbounded response.text(). HTTP status text, parser diagnostics and arbitrary caught exception messages reached console output, lastSyncError and calendarSyncLogs. Existing create/update audit records contain IDs, not feed URLs. Job-creation audit details interpolated the provider UID, which could itself be URL-shaped; this change uses the internal reservation ID instead. Cron/manual scheduling shares admission, cooldown, lease, three-failure suspension and stale-attempt fencing. Failed fetches do not enter reconciliation. Valid-empty checks are non-authoritative and retain reservations/jobs and lastSyncAt.

## Implemented policy and release notes

### URL and address policy

Shared deterministic validation runs on owner create/replacement and again on every fetch/redirect (including legacy stored URLs). HTTPS only, port 443 only, maximum 4,096 characters. Userinfo, fragments (even empty), whitespace/control characters, backslashes, percent-encoded authorities, malformed labels, trailing-dot hosts, single-label/internal names, and noncanonical numeric IPv4 forms are rejected. WHATWG parsing handles IDNA domains and bracketed IPv6. The stored URL and initial/absolute redirect path and query bytes remain intact; relative redirects use standard URL resolution. No query sorting, token stripping or credential rewriting occurs. Raw non-ASCII paths must be percent-encoded. Public IP literals require ordinary TLS IP certificate validation.

IPv4 blocks: 0/8, 10/8, 100.64/10, 127/8, 169.254/16, 172.16/12, 192.0.0/24, 192.0.2/24, 192.88.99/24, 192.168/16, 198.18/15, 198.51.100/24, 203.0.113/24, multicast 224/4, reserved 240/4, and Azure's 168.63.129.16 platform address. IPv6 permits native global unicast 2000::/3, excluding special 2001::/23, documentation 2001:db8::/32 and 3fff::/20, and 6to4 2002::/16. All other IPv6 space, including mapped IPv4, NAT64, ULA, unspecified, loopback, link-local and multicast, is blocked. This intentionally excludes some globally reachable special-purpose addresses. Both literal and resolved addresses use this policy; any unsafe DNS answer rejects the entire destination.

### DNS, TLS and redirects

The existing action already uses the Node runtime. [Convex documents Node action support](https://docs.convex.dev/functions/runtimes#nodejs-runtime); Node provides [HTTPS request options](https://nodejs.org/api/https.html#httpsrequestoptions-callback), [DNS lookup with all answers](https://nodejs.org/api/dns.html#dnspromiseslookuphostname-options), and [socket destination inspection](https://nodejs.org/api/net.html#socketremoteaddress). Address exclusions were checked against the [IANA IPv4](https://www.iana.org/assignments/iana-ipv4-special-registry/) and [IPv6 registries](https://www.iana.org/assignments/iana-ipv6-special-registry/).

For each hop, resolve all answers, reject any non-public answer, then provide a custom HTTPS lookup returning only the selected approved address and family. A fresh one-use agent prevents pooled socket reuse and there is no global-fetch fallback. Hostname, Host header and normal TLS certificate validation remain tied to the provider. Inspect remoteAddress on connect and secureConnect and reject a missing, unsafe or mismatched peer before accepting the response. IPv4-mapped socket representation is normalized only for comparison with a previously approved native IPv4 address; mapped DNS/literal destinations remain blocked. This binds validation to connection establishment rather than performing a pre-check followed by an independent lookup.

HTTPS does not follow redirects automatically. Only 301/302/303/307/308 are followed, with at most three redirects (four requests), loop detection and the complete URL/DNS/socket policy at each hop. HTTPS downgrade, private destinations, credentials and fragments are rejected. Each request sends only fixed User-Agent, Accept and Accept-Encoding headers. No Authorization, Cookie, Referer or original query is copied to another origin. A provider-supplied Location can itself contain its own token; it is never logged.

### Bounds and safe failure behavior

One 30-second deadline spans DNS, TLS, all redirects and body streaming. A cancelled OS DNS lookup may complete in the background, but cannot initiate a request afterward. HTTP response headers are limited to 16 KiB. Reject oversized Content-Length before reading; independently count actual streamed bytes against 2 MiB and immediately destroy request/response on overflow. Cleanup also runs on redirects, HTTP/stream errors, timeout, cancellation and successful completion. Request identity encoding and fail safely if the server insists on compression, preventing decompression bombs. Reject non-2xx, blank bodies, HTML content types and obvious HTML bodies before the existing bounded parser input. Full envelope/event validation stays with PR #270. Valid-empty behavior is unchanged.

Only fixed actionable category messages reach console, connection health and sync logs: invalid URL, unsafe destination, unavailable, timeout, redirects, oversized response, invalid calendar, unsupported encoding or processing failure. Unknown exceptions lose their original text. recordSyncError also allowlists legacy callback strings, while public views and UI sanitize pre-existing errors without modifying historical rows. Sync errors use existing charged-attempt accounting, cooldown, lease, suspension and fencing; they never enter reconciliation or advance lastSyncAt/lastCheckedAt. Existing cron cadence, valid-empty recovery and manual re-enable behavior remain unchanged.

### Credential exposure and compatibility

Connection queries return an explicit operational-field allowlist plus hasFeedUrl, without URL, attempt or cooldown fields. This applies to owners and all same-company staff; cross-company and verified-session protections remain. The unused internal connection query also returns a safe view. Only internal beginSyncAttempt returns the credential to the Node action after atomic admission. Mutations remain owner-only. Plaintext bearer credentials remain in the existing backend storage for synchronization; database operators and privileged internal functions can access them. This PR does not add encryption, rotate credentials, erase historical logs, or claim removal from already-connected old clients' memory.

The owner screen displays a fixed hidden-URL message, allows label/platform editing without supplying the URL, and offers explicit Replace URL with a blank input. The input is cleared on save/cancel and is not cached in local storage. Legacy query URL fields are ignored by the new frontend. Replacement retains connection identity, increments feedRevision only on a changed URL and preserves existing cancellation/fencing rules; invalid replacement is rejected before writes. Existing connections and schema require no migration. Search found no production URL literals or URL-bearing demo/showcase fixtures in application source; regression fixtures use synthetic URLs.

Intended compatibility: ordinary HTTPS Airbnb/Vrbo/other exports, signed query URLs, IDNA domains, public IPv4/IPv6, and safe relative/cross-origin provider redirects. Intentionally unsupported: HTTP, custom ports, internal/VPN feeds, special-purpose address space, >4,096-character URLs, >2 MiB feeds, >3 redirects, servers requiring compressed responses, and non-percent-encoded Unicode paths. No real customer/provider feed was fetched; synthetic tests are not provider certification. No classification, missing-event grace, identity, job scheduling, timezone or payment policies changed.

### Runtime limitations and release gate

No deployment or live-provider request was performed. Mocked Node transport tests verify pinning callbacks, all-answer checks, peer checks, redirects, streaming limits and cleanup, but do not certify Convex's deployed egress implementation or provider compatibility. Before approval for production release, validate an authorized synthetic public HTTPS feed in a non-production Convex deployment. Confirm that the deployed Node version supports the DNS/HTTPS imports, all-answer DNS resolution, the custom pinned lookup/family callback, and connect/secureConnect remoteAddress inspection. Verify that egress honors the selected address while retaining provider hostname/SNI/certificate checks, and exercise safe redirects, streaming overflow, stalled requests and abort cleanup against controlled public fixtures. These deployed-runtime checks remain outstanding; no SSRF protection is production-certified. If the platform cannot expose/retain the pinned connection, this implementation fails closed; do not substitute an ordinary fetch after a DNS pre-check. A trusted egress proxy or provider-specific connector would then be required for stronger guarantees and would need separate approval.

Public endpoints can themselves act as proxies, DNS/IP allocations can change, and networking/NAT behavior outside the process cannot be certified here. Maintain the address policy with future IANA changes. This is materially stronger connection-level SSRF containment, not a claim of universal network isolation. Privileged backend logging/invocation tooling and provider access logs may still see URLs as necessary request inputs; no new application error/audit output includes them.

### Deployment and rollback (recommendation only)

After review/approval, first validate the above non-production runtime gate. Prefer merging with automatic frontend promotion held, then deploying this Convex backend before promoting the matching frontend, instead of the usual merge → Vercel → Convex order. The backend closes the unrestricted-fetch and staff credential-return paths immediately; frontend-only release would leave them open. The new frontend tolerates either query shape, but an old frontend receiving the new safe view cannot prefill a URL during Edit; existing sync still works, and users can paste a replacement during that brief interval. Promote the matching frontend promptly and reload old sessions. No schema/data migration is necessary.

For UI-only trouble, roll back the frontend while retaining the hardened backend, accepting that temporary Edit limitation. Prefer a forward fix for transport issues. Reverting the backend reopens credential exposure and unrestricted SSRF fetching; it must be an explicit reviewed incident decision, not an automatic frontend rollback. There is no production data rollback to run. Do not disable feeds or rotate secrets as part of this PR.

# Microsite public PDF inspection

Company Documents remains the canonical file owner. The My Site picker uses the same upload intent, candidate registration, and finalization workflow as the Documents hub. Saving, hiding, or removing a microsite listing does not create a copy or modify private client assignments. Existing documents have no public designation. An owner designates a PDF by requesting its check, acknowledges that anyone can download the exact version, and saves a visible entry on a published site.

## Settings and responsibilities

Verify the Vercel project's Node runtime supports the pinned Sandbox SDK `5.0.0` (Node 22.19 or newer). Both SCRUB Vercel projects use Node 24.x. Verify Secure Backend Access with OIDC in the target project's settings. The SDK uses the project-scoped Vercel OIDC identity outside the guest. The inspection guest receives neither OIDC nor application credentials.

Set `NODE_OPTIONS=--experimental-require-module` on the deployment running the worker. Vercel disables this Node capability by default, and the pinned SDK's CommonJS Drives dependency uses it to load the ESM-only Workflow serialization module. Confirm that the deployed worker returns its empty 404 with missing and invalid service keys before provisioning a snapshot. [Vercel Node.js configuration](https://vercel.com/docs/functions/runtimes/node-js/advanced-node-configuration#experimental-node-js-require-of-es-module)

Provision a **dependency-only** snapshot in each target Vercel project. From an authenticated shell with that project's short-lived OIDC context, run `node scripts/provision-microsite-pdf-snapshot.mjs`. The script pins the official Python sandbox base digest, downloads the official QPDF 12.4.2 Linux amd64 ZIP, verifies SHA-256, verifies the executable version, closes egress, and snapshots the dependency-only VM. The official SDK supports `expiration: 0` for indefinite retention. Pin the returned snapshot ID in the worker configuration. This removes calendar-based rotation and needs no scheduler or standing rotation credentials. The inspector starts a fresh nonpersistent VM from that artifact for each job. A customer-processing VM must never be snapshotted or reused.

Retain one active dependency snapshot per configured project and at most one previous snapshot during an intentional update. On a dependency update or security advisory, review and pin the new inputs, provision the replacement, verify its provenance and behavior in development, and switch the configured snapshot ID. Review the upstream QPDF Apache-2.0 and third-party notices as part of that update. Where a policy or inspector version must change, follow the reinspection procedure below. Delete the superseded snapshot after verification and the brief rollback window. Delete failed candidates and development-only artifacts when the exercise ends. Verify the active ID before deleting any snapshot, and remove the active snapshot when the feature is retired. No recurring provisioning or per-inspection registry work is required. [Vercel SDK snapshot retention](https://vercel.com/docs/sandbox/sdk/javascript#snapshot)

| Environment | Key | Meaning |
| --- | --- | --- |
| Convex and matching Vercel environment | `MICROSITE_PDF_WORKER_KEY` | Same random, environment-specific service key of at least 32 characters. Scope it to the two inspection endpoints. Keep it separate from deployment keys. |

The Convex action sends only an inspection ID and nonce to Vercel. Vercel requests the bytes from the private Convex endpoint, avoiding Vercel's default incoming payload limit. Convex checks the one-time claim, immutable storage ID, company, current designation, status, and measured size before supplying the file. Only the trusted function handles the credentials. It verifies deny-all networking and nonpersistence before writing bytes through the Sandbox control plane. It launches the fixed parser with one vCPU, no ports or drives, 35 seconds of platform lifetime, and a 12-second command deadline. Shutdown is attempted in a finally block. The sandbox never creates a snapshot. A provider timeout can take additional time to show as stopped.

The job stores version identifiers and a small outcome, with time and attempt count. A first check is scheduled independently of the owner page. Concurrent checks reuse the same generation. Rejections are reused for the same storage ID, policy, and inspector. The owner can explicitly retry one transient failure. Bump the policy or inspector version if protection changes or an advisory requires reinspection. Existing passing results under the former policy cease to authorize downloads immediately. If responding to a consequential issue, suspend new inspections, suspend affected public transfer, update the dependency and policy versions, then require owners to check and approve the affected file versions again.

## PDF profile and residual risk

- Eligibility requires an active canonical PDF of at most 10,485,760 bytes. No private filename or document ID is in the public URL, card, or attachment filename.
- QPDF runs with cross-reference recovery disabled. Warnings and errors fail closed. A second run exports the object graph, including supported compressed objects. The policy rejects encrypted files, embedded or external files, action and annotation trees, forms, JavaScript, launch, rich media, unsupported stream filters, incremental or hybrid trailers, and ambiguous or unsupported structures. Only Flate and JPEG stream filters are allowed in this initial profile. PDFs with links, forms, or unsupported exports may need a new static export.
- Each parser process has a 256 MiB address-space limit, 3 CPU seconds, 4 wall seconds, a 24 MiB file-output limit, 32 descriptors, and core dumps disabled. The wrapper has a 384 MiB address-space limit. The 24 MiB serialized graph cap also bounds fully decoded stream bytes emitted by QPDF. JPEG image data remains a compressed payload under the generalized decoder. Parser object and nesting limits, 12,000 top-level graph records, and 120,000 traversed nodes provide additional bounds.
- Guest diagnostics can contain PDF material and remain in short-lived guest scratch files. The guest emits one status word. The application never stores a PDF copy or parser output. Structural inspection and attachment delivery leave residual malware, reader vulnerabilities, and retained download risk.

## Limits, billing, and monitoring

Ten entries per site, 100 characters for public titles, 320 for descriptions, and 80 for section headings. Inspection limits are 10 launches per company per hour, 250 launches per UTC day across the deployment, 3 active leases across the deployment, and 2 attempts for one exact file and policy. These caps apply before scheduling billed work. Expired leases fail closed. Set the internal `micrositeResources:setInspectionSuspension` switch to suspend new inspections and unclaimed transfers. An owner changing display text or visibility never starts an inspection.

Downloads are on demand and return attachment, no-store, nosniff, and noindex headers. Every request verifies the current site and section visibility, entry, owner-approved exact file version, passed policy result, file existence, and suspension. The Phase 3A operator suspension covers both documents and images. PDFs have a separate 128 MiB hourly company allowance, so document traffic cannot consume the existing 512 MiB image allowance. Requests over the PDF limit receive 429. A replacement, archive, removal, or hide revokes the old URL on subsequent requests. Archived files require explicit approval again after restoration.

Plan for one Vercel Function invocation, one authorization-constrained Convex file read, plus Convex job state and worker calls per launch. A typical 1 MiB file adds about $0.13 in Convex data egress per 1,000 inspections at $0.12/GB after included usage. Ten MiB per inspection adds about $1.26 per 1,000. The earlier sandbox case measured 2.2 active CPU seconds and 6.9 seconds elapsed across the synthetic matrix. A hypothetical 1,000 one-vCPU sessions at that CPU usage and a one-minute billed 2 GB allocation would cost about $0.79 in sandbox compute at published iad1 rates. The measured 181 MB dependency snapshot would add about $0.015 per month at $0.08/GB-month. Function compute, platform transfer classifications, retries, and usage credits affect actual spend. The billing API returned no finalized charges for the QA runs.

Indefinite retention leaves the storage rate and normal steady-state count unchanged. At the measured size, one retained artifact costs about $0.015 per project-month, including months with no use, and two retained for a full month would cost about $0.029. Delete the previous artifact promptly after an intentional update to keep overlap short. Inspection compute, transfer, and application limits are unchanged. Provisioning is only needed for setup or an intentional dependency update. [Vercel Sandbox pricing](https://vercel.com/docs/sandbox/pricing)

Before release, configure and confirm Vercel spend alerts, Sandbox usage dashboards, and Convex usage thresholds with the founder. Monitor sandbox creations, CPU, billed memory, retained snapshot count and size, dependency security advisories, Convex file egress, unavailable-result rates, and circuit-breaker trips. Direct Convex delivery is outside Vercel WAF.

## Hosted development end-to-end release check

Before deploying a worker change, run the packaged Function test with Node 24 and the locked workspace dependencies installed. Install `@vercel/node@34.0.0` in a scratch directory, then run `node scripts/test-microsite-pdf-function-bundle.mjs <scratch>/node_modules/@vercel/node` from the repository root. It loads the emitted Vercel Function in a fresh Node process and verifies that missing and invalid authorization return 404 before any file transfer. The test also checks that the artifact contains the shared policy contract within the frontend ESM workspace and excludes Convex backend modules.

**Request founder approval before deploying.** Deploy the exact PR commit's frontend and `/api/microsite-pdf-inspect` Function to a development-only deployment of `scrub-dev`. Build with `npm run build:frontend` for the Vercel deployment. Push that same commit's Convex schema and functions separately to an isolated hosted Convex development deployment. Point the frontend's `VITE_CONVEX_URL` and `VITE_CONVEX_SITE_URL` and the worker settings above to that pair only. Configure a unique test worker key on both sides, a clean snapshot in `scrub-dev`, and the development frontend origin for the canonical upload and private download flow. Verify that the Convex scheduler can reach the exact Vercel worker URL without a redirect. If Deployment Protection blocks server-to-server traffic, stop and coordinate a separately approved development-only access method. Keep the worker's own authorization intact. Leave production deployments, aliases, settings, and data out of the exercise.

1. Create a synthetic owner and microsite on the hosted frontend. Upload one passive synthetic PDF through My Site, then select that existing canonical resource. Save the visible listing before approval and verify it does not appear publicly.
2. Use **Check document** in My Site and verify the resulting Convex inspection is bound to that canonical file version. Correlate one scheduled action with one authorized Vercel Function invocation, one successful claim of the exact canonical bytes, and one matching Vercel Sandbox session. Confirm deny-all networking, one vCPU, nonpersistence, no ports or mounted drives, and a stopped session with no customer snapshot. Record only timestamps, status, and nonsecret IDs. An SDK probe, manually completed inspection, mocked response, or local fixture does not satisfy this check.
3. Wait for the hosted worker's actual result to change the Convex record to `passed` and the owner UI to show that the document meets publication requirements. Verify it still does not appear publicly. Acknowledge public download access, approve the file version, and save. In a signed-out session, open the public microsite and download the PDF. Compare its SHA-256 to the original synthetic fixture and check the attachment, no-store, nosniff, and noindex headers.
4. Download again and edit the listing title or visibility. Verify no new inspection, sandbox, canonical record, or stored file was created. Hide the entry and verify the previous URL returns 404. Restore visibility and replace the canonical file, then verify the old approval no longer works. Check a deliberately disallowed synthetic PDF through the same hosted flow and verify the real result is `rejected` and approval remains unavailable.
5. Record the PR SHA, deployment identities, and evidence for each hop. Remove the synthetic data, development-only artifact, and temporary test credential after verification, and tear down any deployment created solely for this exercise.
